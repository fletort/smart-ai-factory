# Skill Unit Test Strategy - Developer Guide

This document provides detailed information about the unit and integration testing strategy for
**Skills** in the `smart-ai-factory` repository. It is designed for developers who need to
understand, maintain, or add new tests for LLM-based agent skills.

## Context & Objectives

In `smart-ai-factory`, **Skills** (such as `smart-spec` under `.agents/skills/smart-spec/`) are
interactive, multi-turn LLM agents. They are designed to interact with users and perform system
tasks by executing tool calls (e.g., `read_file`, `write_file`, and `directory_content`).

Testing LLM-based agent skills presents unique challenges:

1. **Multi-turn interactions**: Real usage involves several rounds of interaction (user messages,
   tool calls, tool responses).
2. **Determinism**: We must verify that skills request correct tool calls and generate correct
   messages without suffering from LLM randomness.
3. **Sandbox isolation**: Executing real files edits and reading active workspace state during
   automated testing is complex and can lead to side effects.
4. **Cost & Latency**: Running real LLM agent loops over multiple external API calls is slow and
   expensive.

To solve this, our testing strategy **mocks and simulates the multi-turn interaction** by passing
pre-constructed interaction histories to the LLM and asserting on the very next turn generated by
the model.

## Architecture Overview

The test suite is organized under the `tests/` directory with a specific focus on prompt evaluation
and simulation:

```text
tests/skills/
├── gemini-quota.sh                   # Quota health-check & dynamic config script
├── configs/                          # Shared configurations, mocks, and custom providers
│   ├── prompts/
│   │   ├── 01-first_message.txt      # Text-only baseline prompt template
│   │   ├── 02-get_config.chat.json   # Simulated chat history for config retrieval
│   │   └── prompt.js                 # Dynamic prompt and history loader
│   ├── providers/
│   │   ├── geminiOpenAiProvider.js   # Custom Gemini-to-OpenAI protocol adapter
│   │   └── gemini-openai.test.js     # Unit tests for the custom adapter
│   ├── tests/
│   │   └── read_config_first.yml     # Common test assertions (e.g. config file checks)
│   └── tools.yml                     # Mock definitions of skill tool definitions
└── smart-spec/                       # Tests specific to the 'smart-spec' skill
    ├── prompts/
    │   ├── 03-get_spec.chat.json     # Mock history: drafting specifications
    │   └── 04.chat.json              # Mock history: finalizing specs (index + spec write)
    └── promptfooconfig.yaml          # Promptfoo configuration for 'smart-spec' tests
```

The pipeline uses **Promptfoo** to orchestrate evaluations and assertions across different LLM
providers.

## Mocking Multi-Turn Interactions

Instead of running an active agent loop, we structure our test prompts as a **sequential history of
messages** (using the standard OpenAI chat JSON format). We feed this history to the LLM, making it
believe it is already in the middle of an interaction. The model then generates the next response or
tool call, which we validate.

### Message History Structure

A typical mock history under `prompts/*.json` represents an array of chat messages:

1. **System Instructions & User Init**: The first message sets up the core prompt (`SKILL.md`
   contents) and the initial user request.
2. **Mock Tool Call**: An `assistant` message representing a tool call (e.g., `read_file` for
   `.smart.ai/conf.yml`).
3. **Mock Tool Output**: A `tool` response representing the mock data returned from that tool.
4. **Subsequent Conversation**: Simulates any further turns to reach the target state.

#### Example: `02-get_config.chat.json`

```json
[
  {
    "role": "user",
    "content": "# SYSTEM INSTRUCTIONS\n{{skill_prompt}}\n# ASSOCIATED USER MESSAGE\n{{user_message}}"
  },
  {
    "role": "assistant",
    "content": "",
    "tool_calls": [
      {
        "id": "call_1",
        "type": "function",
        "function": {
          "name": "read_file",
          "arguments": "{\"path\": \".smart.ai/conf.yml\"}"
        }
      }
    ]
  },
  {
    "role": "tool",
    "tool_call_id": "call_1",
    "name": "read_file",
    "content": "{{read_file_config_result}}"
  }
]
```

By changing variables like `{{read_file_config_result}}` or the final user answer, we can test
different branches of the skill's decision tree (e.g., missing config vs. valid config, unified vs.
modular template).

## Key Components & Shared Tools

### 1. Dynamic Prompt Loader (`prompt.js`)

Located at `tests/skills/configs/prompts/prompt.js`.

This Node.js script is registered as the prompt source in `promptfooconfig.yaml`. When Promptfoo
runs a test case, it delegates the prompt resolution to `prompt.js` with the context variables
(`vars`).

**Key Responsibilities:**

- Dynamically loads prompt files from `vars.prompt_path`.
- Implements **model-specific fallbacks** depending on the provider, model label, or configured
  grammar type (e.g., loading a grammar-specific strict JSON prompt format or a standard fallback).
- Automatically parses `.json` files into structured OpenAI-style chat formats or returns raw `.txt`
  / `.md` content.

**Resolution Priority order:**

1. `<vars.prompt_path.name>.<provider.config.grammar_type>.<vars.prompt_path.ext>`
2. `<vars.prompt_path.name>.<provider.label>.<vars.prompt_path.ext>`
3. `<vars.prompt_path.name>.<sanitized_provider_id>.<ext>`
4. Original fallback path: `<vars.prompt_path>`

### 2. Custom Gemini Provider (`geminiOpenAiProvider.js`)

Located at `tests/skills/configs/providers/geminiOpenAiProvider.js`.

Promptfoo's standard chat interface operates primarily on the OpenAI message schema. To test Google
Gemini models directly while retaining a unified test configuration, we use a custom provider
adapter.

**Key Responsibilities:**

- **Input Mapping**: Translates standard OpenAI messages (system instructions, tool calls, and tool
  responses) into native Google Gemini API format (`contents` and `systemInstruction` structure).
- **Tool Mapping**: Correctly merges consecutive tool responses into single roles, maps parallel
  function call formats, and injects specific `thoughtSignature` exceptions where necessary.
- **Output Mapping**: Maps Gemini's returned function call format back to standard OpenAI-compatible
  tool call structures.
- **Unit Tested**: The adapter mapping logic is fully tested via standard Node.js test runner at
  `tests/skills/configs/providers/gemini-openai.test.js`.

### 3. Quota Management & API Safeguards (`gemini-quota.sh`)

Located at `tests/skills/gemini-quota.sh`.

Free tier AI provider API limits (such as Google Gemini) can easily fail in automated pipelines.

**Key Responsibilities:**

- Performs a lightweight "health check" query to the Gemini API before running the test suite.
- If the quota is exceeded (HTTP 429) or fails, it **dynamically modifies the test configuration
  (`promptfooconfig.yaml`)** by commenting out the `gemini` provider line.
- If the API check succeeds, it ensures the `gemini` provider is uncommented/enabled.
- This ensures test suites degrade gracefully and fallback to alternative providers (such as
  DeepSeek via OpenRouter) rather than breaking the test run.

## Defining Assertions & Validations

To verify that the model's next turn is correct, we use Promptfoo's rich set of assertion types:

- **Structure Validation**:
  - `is-json`: Verifies the model outputs valid JSON (useful when validating structured tool
    parameters).
- **Content Matching**:
  - `contains` / `contains-all` / `contains-any` / `not-contains`: Checks for the presence (or
    absence) of specific strings, keywords, or paths in the output.
- **Tool Call Inspection**:
  - We use JavaScript transforms (`transform: ...`) inside assertions to check if specific functions
    are called with precise parameters. For instance:

    ```yaml
    - type: equals
      value: '.smart.ai/conf.yml'
      transform: |
        const args = output[0].function?.arguments;
        argsJson = typeof args === 'string' ? JSON.parse(args) : args;
        return argsJson.path
    ```

- **Semantic Validation**:
  - `llm-rubric`: Leverages a grader LLM to evaluate complex, natural language specifications (e.g.,
    verifying that a drafted specification matches all user goals and answers all high-impact
    questions).

## Common Developer Workflows

### 1. Run Custom Provider Unit Tests

To run the Node.js unit tests verifying our Gemini-to-OpenAI mapping logic:

```bash
# Ensure dependencies are installed
npm install

# Run the test suite
node --test tests/skills/configs/providers/gemini-openai.test.js
```

### 2. Run Skill Promptfoo Evaluations

To run promptfoo tests for a specific skill (e.g., `smart-spec`):

```bash
# 1. Run the Gemini quota health check to adjust promptfooconfig.yaml dynamically
./tests/skills/gemini-quota.sh

# 2. Run Promptfoo evaluations
npx promptfoo eval -c tests/skills/smart-spec/promptfooconfig.yaml
```

To view the results in a local web dashboard:

```bash
npx promptfoo view
```

## Guidelines for Testing New Skills

When adding a new Skill to the repository, follow these steps to add its test suite:

1. **Create Directory**: Create a folder `tests/skills/<skill-name>/`.
2. **Setup Configuration**: Create `promptfooconfig.yaml` referencing the global loader and
   configurations:

   ```yaml
   # yaml-language-server: $schema=https://promptfoo.dev/config-schema.json
   description: 'Test <Skill-Name>'

   prompts:
     - file://../configs/prompts/prompt.js

   providers:
     - id: file://../configs/providers/geminiOpenAiProvider.js
       label: gemini
       config:
         model: 'google:gemini-3.6-flash'
         apiKey: '{{ env.TEST_GEMINI_API_KEY }}'
         tools: file://../configs/tools.yml
     - id: openrouter:deepseek/deepseek-v4.1-flash
       config:
         apiKey: '{{ env.TEST_OPENROUTER_KEY }}'
         tools: file://../configs/tools.yml
         showThinking: false
         max_tokens: 8000

   defaultTest:
     vars:
       skill_prompt: file://../../../.agents/skills/<skill-name>/SKILL.md
     options:
       provider: openrouter:deepseek/deepseek-v4.1-flash
   ```

3. **Write Prompts**: Define sequential message history templates under
   `tests/skills/<skill-name>/prompts/`.
4. **Define Test Cases**: Specify your target scenarios, input variables, and assertions. Leverage
   `tests/skills/configs/tests/read_config_first.yml` if your skill checks workspace config first.
5. **Add to CI/CD**: Ensure the new skill configuration is run as part of the automated testing
   pipeline if/when integrated into workflows.

## Troubleshooting

### Gemini Quota Errors in Tests

If Gemini fails with rate limit errors (HTTP 429), run `./tests/skills/gemini-quota.sh` to update
the config file before starting promptfoo. The tool will automatically skip Gemini and run
assertions on DeepSeek or other configured providers instead.

### Missing `promptfoo` Dependency

If you get `MODULE_NOT_FOUND` errors when executing provider tests, ensure Node dependencies are
fully up to date:

```bash
npm install
```

### Incorrect Tool Arguments Format

Since different models can format arguments with subtle whitespace or quotes variance, use standard
JSON parsing inside Javascript `transform` properties in your assertions to extract arguments
robustly (instead of checking exact string matches on `arguments`).
